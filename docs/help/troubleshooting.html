Troubleshooting

Symptom, cause, fix. Almost everything here is confirmed by the log — logs\synapic.log next to the executable — so start by opening it.

First, two rules

  • If a field is missing, check Step 2 before anything else. The write step keeps only the tag fields you ticked, and does it silently. See Tag fields.
  • If it is slow, check what else is running. Four images are in flight at once, first runs download and load a model, and a batch competes with everything else on the machine. See speed and timings.

The inference server

SymptomCause and fix
Wizard is greyed out; Inference sidecar requiredNo inference server exists. Build one from the setup panel: Build the inference server.
Server not detected and nothing to buildNo server executable for this platform. Install a release that includes one, or drop a standalone server next to Synapic.exe.
Build stops part-way, rows stay on Not builtThe build log is in the log pane. A first build needs the network to fetch Python and the inference packages; a later failure is often disk space. Rebuild once the cause is gone.
Server starting… for more than two minutesA cold start unpacks and loads the model, which is genuinely slow the first time. If it never resolves, the log contains the server's own output — usually a missing model or a driver problem.
Timed out waiting for the sidecar port fileThe server process never got far enough to publish its port. Look a few lines up in the log for its error: a corrupted build, an antivirus quarantine, or no write access to the temporary folder.
Sidecar process exited unexpectedlyThe server crashed mid-run. Restart it from the toolbar; if it repeats on the same image, that image is the suspect — a truncated or unusual file.
Model loading — retry shortlyThe server is still loading the model. Wait for it to report healthy; Synapic retries the request once by itself.
stale build, rebuild recommendedDeveloper checkouts only: the server executable predates the inference source. Rebuild that variant.

Tags that are missing or wrong

SymptomCause and fix
Only keywords were writtenThe Step 2 tag-field selection. Check the boxes, the orange warning, and the batch's first log line: the diagnosis recipe.
Category or description is empty for every imageA custom tag instruction that stopped asking for those keys. Press Reset to built-in in Step 2 and run one image to confirm.
Keywords came back empty although the description looks fineSame cause: with a custom instruction, the reply can be valid JSON without a keyword list. The server logs a warning when this happens; reset to the built-in instruction.
Raw JSON or code fences appear in the descriptionThe model's reply could not be read as the expected shape — almost always a custom instruction or system prompt that asked for a different format. Clear both.
Descriptions are vague and genericThe image was downscaled too far. Raise AI image scale to 100% and turn off the 200-pixel thumbnail: How many items to process.
Categories are plausible but not your vocabularyThe model is not constrained to a list. Steer it with a system prompt, or curate categories by hand — see Step 4.
A run finishes suspiciously fast, with no resultsThe batch found nothing. The log says Found 0 image files or reports no matching items; check the folder path, the scope and the filters.

Daminion

SymptomCause and fix
Connection failedWrong URL (include the scheme and the virtual directory), server unreachable, or bad credentials. See Connecting to Daminion.
Connected, but the collection or saved-search lists are emptyThose endpoints did not answer. Tagging still works: type the id in the small box beside the picker.
Count looks wrong, or counting failsThe count is a server-side preview. If it fails, the batch still applies your filters; check the newest log line for the reason.
Daminion returned the same ids as the previous pageThe server ignored the paging offset. Synapic stops rather than looping; the batch covers the items fetched so far, so narrow the scope and run again.
Could not download image for item 12345The item exists but its image could not be fetched: a permissions problem, or a file the server cannot find.
Items are updated but keywords are missing in DaminionLook at the write path rather than the model: check the tag-field selection, then whether the account may write keywords. Verify Daminion Writes in Step 4 reports what the catalog actually holds.

Speed and timings

SymptomCause and fix
Five to ten seconds per image on CPUNormal for the default model. Up to four images run at once, so the batch finishes four times faster than that per-image figure suggests.
One image appears to take a minuteThe first image includes the model download (once, about 860 MB) and the load. Judge timings from the second image on.
Every run is slower than the one beforeSomething else is using the machine, or the batch is fetching over a slow link. Sort the Daminion case by using the 200-pixel thumbnail for the first pass.
GPU build is not dramatically fasterExpected in some cases: four parallel calls can contend for one GPU, and a small model is often not GPU-bound. Compare on a real batch before drawing conclusions.
Memory climbs and the machine swapsLarge images at 100% scale, or several batches in one session. Restart Synapic between large runs to release the inference server's memory.

Failed writes and retries

SymptomCause and fix
Rows with status Write FailedThe image was tagged but could not be written: a read-only file or folder, a file in use, or a metadata update Daminion refused. Fix the cause, then Retry Failed.
Retry Failed does nothingIt only retries rows that are not successes. If every row succeeded, there is nothing to do.
Retrying fails the same wayThe source is the problem, not the moment. Check the file exists, is readable, and is not locked by another application.
Verification reports mismatchesThe catalog does not hold what Synapic wrote. Check permissions on the account, and whether another process or a deduplicating tool has since changed those items.
CSV export says nothing happenedExport needs at least one row. Run a batch first.

Nothing else worked: what to collect

  1. logs\synapic.log for the run in question.
  2. The archived log before it, if the problem started earlier: logs\archives\.
  3. Anything in logs\crashes\, which holds the exception and a snapshot of the log at the moment of a crash.
  4. A one-line description of what you expected and what happened, including the settings on screen — or simply the batch's first log line, which records them.
