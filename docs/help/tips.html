Tips and useful info

The things experienced users keep in their pocket: how to make a run faster, how to make the tags better, and how to avoid the two or three mistakes that cost an afternoon.

Speed

The first batch is always the slow one.

It downloads the model (about 860 MB), unpacks the built server and loads the weights. Later batches start tagging in seconds. Timings that look alarming on run one are usually this, not a fault — Speed and timings has the real numbers.

LeverEffectWhen to pull it
Device: CUDA or MPSThe single biggest win — an NVIDIA GPU turns minutes into seconds per batch.Whenever the machine has a GPU; the CPU build still works everywhere.

Concurrency: the app tags images in parallel slots, so the last stretch of a batch can look uneven while slots drain. The progress bar counts finished items, not started ones. See Running a tagging batch.

Better tags

  • Prompt small, test small. Change one thing, run a dozen images, look at the result. The recipe: Trying prompt changes without wasting a batch.
  • The system prompt sets the scene; the tag instruction sets the contract. Style and domain ("botanical plates, 19th century") belong in the system prompt; the output shape belongs to the built-in instruction. See Prompts.
  • Check the tag fields before blaming the model. If a field is missing, the first suspect is the matching unticked box in the engine section, not the prompt: the diagnosis recipe.
  • Candidate labels pin the vocabulary. If the keywords drift into synonyms you did not want, give the scorer the exact list (candidate labels) instead of arguing with the model.
  • Raise the confidence threshold for precision, lower it for recall. Too many marginal keywords? 0.3 → 0.4. Missing the obvious ones? Try 0.2: confidence threshold.
  • Descriptions tell you what the model saw. A vague generic description almost always means the image was scaled too far down (AI image scale), not that the prompt is wrong.

Working safely

There is no undo.

Writes go straight into the files or the catalog, and a re-run replaces the fields Synapic manages rather than merging. Keep a backup before the first large run, and rehearse on copies — see the FAQ and What gets written to your images.

  • Count before you run. The record count under the source panel answers "how much work is this?" and keeps itself current as you change the scope. So does the summary line in the report afterwards.
  • Rough pass now, proper pass later. A 200px thumbnail triage over the whole catalog, then a full-scale run over the saved search that matters, is a legitimate plan — the second run overwrites the first rather than adding to it.
  • Verify writes into Daminion. The Verify Daminion Writes button re-reads what the server actually has, which settles "did it really save?" without opening the catalog by hand.
  • Failed rows are retryable. The report's Retry Failed re-runs exactly the rows that broke (transient errors, a dropped connection) without touching the successes.

Catalog and workflow

  • Let a saved search do the triage. Scope is the steering wheel: build the "needs keywords" set as a saved search once, then every later pass selects it instead of re-filtering. See Deciding what to process first.
  • Untagged filters beat careful scoping. The three Only items with untagged… boxes make a run idempotent in practice: re-running them skips everything already done. See untagged filters.
  • Process all, but count first. Process all pages until the server runs dry — correct for big catalogs, surprising if the scope was wrong. Count, then commit: How many items to process.
  • Status filter = who reviews the output. Run Unassigned items first; leave approved material alone unless the taxonomy changed.
  • Duplicates waste the most time. Dedup the folder before a first pass and you tag each photo once, not three times: Deduplication.

Housekeeping

ThingGood to know
Saved prompt historyHighlight an entry in the engine section's presets dropdown and press Delete to prune it — the list is its own file (%APPDATA%\Synapic\system-prompts.json), never your current settings. See Prompts.
Logslogs\synapic.log next to the app; the previous ten runs are rotated into logs\archives\ and crash snapshots land in logs\crashes\. Nothing is ever uploaded. See Logs, crashes and support.
Model cache%LOCALAPPDATA%\Synapic\models (off Windows: ~/.cache/synapic/models) is shared by every Synapic install for your user. Deleting it re-downloads — it is disk, not configuration.
UpdatingRe-running the installer upgrades in place; settings survive because they live outside the install folder (registry + config.json). The sidecar updates from its own row: Build sidecar and Download while a row is missing or outdated, a disabled Up to date marker when it is current. See Installing and upgrading.
Support requestsThe log, one crash file and the config.json say almost everything a helper needs — see Nothing else worked: what to collect.
