Get the inference server

The model does not run inside Synapic. It runs in a second program, the inference server, which Synapic starts and talks to over a local port. Until one exists, the rest of the app is disabled on purpose.

Why there is a separate server

The model needs a Python deep-learning runtime — hundreds of megabytes of native libraries that have nothing to do with a desktop UI. Keeping them in their own process means the app starts instantly, and a crashed model cannot take your batch down with it. Synapic spawns the server, waits for it to report healthy, sends it one request per image, and shuts it down when the app closes.

You only see it in two places: the status dot at the bottom of the sidebar, and the Inference server section in the Settings view.

Download one — automatically on a first run

On a machine with no server yet, Synapic does the first download without a button press: it picks the variant that suits the machine — CUDA (NVIDIA GPU) when an NVIDIA driver is present, the CPU build otherwise — fetches it, and starts the server when it lands. That row carries a Recommended for this machine note. The whole sequence is logged in the app log, and the transfer shows its own progress bar and stage, so the app is never silently working.

You keep full control: press Cancel download on the row to stop it, choose a different row, or turn the automation off with the Download a missing sidecar automatically switch in the Inference server section. With the switch off (or now after one attempt this session), downloading is entirely by hand, as follows.

  1. Look at the Inference tab in the Settings view. Each row under Platform variants is a server you can run on this machine: CPU (runs anywhere) and, on Windows, CUDA (NVIDIA GPU) (much faster on a supported card). The small grey text next to the name is the variant's runtime identifier, for example win-x64 or win-x64-cuda.
  2. Press Download on the row you want. Synapic fetches the executable the GitHub release already published: about 216 MB for CPU, and for CUDA (NVIDIA GPU) two large parts that Synapic joins for you. Nothing on the machine needs Python, the packages, or a source checkout.
  3. Watch the row. It shows a progress bar and the current stage, such as Downloading part 1 of 2. While the transfer is active, use Cancel download on that row to stop it. A cancelled or failed download leaves the row available to try again.
  4. When the row reads Built with a size, the server can start. Synapic starts it automatically on the next app launch, or press Start Server; the status text moves to Server running (port …).

Downloaded servers are stored per variant in your own data folder — %LOCALAPPDATA%\Synapic\sidecars\<variant>\ — which Synapic can always write to, and where the two variants stay side by side instead of replacing each other. A server bundled with the installer sits next to the app and keeps working regardless.

Synapic also checks GitHub for a newer prebuilt server every time it starts. When the release page carries a fresher executable than the one on disk — or no executable exists yet — a gold note appears on the row naming the release (for example nightly), and the row offers Download again. The check never blocks startup: if GitHub is unreachable it stays silent.

Building from source is a developer workflow now.

The repository still carries the build pipeline (build/build-sidecar.ps1), and the app still refuses to launch a server executable older than the Python source in a developer checkout, but the Build button is gone from the interface: GitHub's release builds are the shipped path, and keeping a parallel in-app toolchain only added a failure mode to the first run. To replace the server by hand, drop a downloaded synapic-inference.exe next to Synapic.exe and restart Synapic.

Which variant should I download?

VariantWhen to choose it
CPUAlways a safe choice. Works on every machine, needs no GPU driver, and is what a machine without an NVIDIA driver gets automatically. Tagging takes several seconds per image.
CUDA (NVIDIA GPU)When the machine has an NVIDIA card with a current driver — which is exactly what Synapic recommends and fetches automatically on such a machine. The download is larger (about 2.5 GB), and it falls back to CPU if no usable GPU is present, so it is safe to install anywhere.

You can have both.

Building both is normal for a workstation: use the CUDA variant day to day and keep the CPU one as a fallback. They are independent executables and the build of one cannot break the other.

Which one runs is decided by the Device control in Settings › Tagging: with CUDA selected, Synapic starts the CUDA executable; any other setting starts the CPU one. The status bar names the device the running server reports, so a fallback is visible rather than silent.

Updating or replacing the server

When a row is outdated — the startup check found a newer prebuilt on GitHub (the gold note) — that row offers Download to fetch the released executable. Synapic stops the server if it is running, replaces that variant's executable, and starts the server again on the replacement.

When a row is already current, no action is offered: the button is relabelled Up to date and disabled, because there is nothing to fetch. The moment the release moves ahead, the row opens Download again.

You can also do it by hand, which is the way to pin a specific release rather than the newest one. The server is one self-contained executable: put the new file next to Synapic.exe, named synapic-inference.exe, replacing the existing one, then restart Synapic — for example switching a workstation to the CUDA build after buying a GPU.

Do not delete the server while Synapic is running.

A running batch will fail image by image. Press Stop Server in the Settings view first, close Synapic, then replace the file.

The model itself

Downloading a server does not yet fetch the model. Once the server starts, Synapic hands it the machine's model cache folder, and the server downloads the shipped model (about 860 MB) in the background — a boot usually completes before the model is finished. Progress for both appears live in the sidebar: Downloading model: 310 / 860 MB (36%). The model is cached per machine under %LOCALAPPDATA%\Synapic\models. Later runs, and other installs of Synapic on the same machine, reuse it.

Organisationally this matters in two cases: moving a machine to a faster variant does not re-download the model, and a machine with no internet access needs that folder seeded before it can tag anything. See Deploying to many machines.

When something looks wrong

What you seeWhat to do
Server not detected and no rows at allThere is no source checkout and the latest release has nothing for this machine's platform either. Install a release build that includes one.
Download fails part-wayThe log drawer names the release, the asset and the HTTP status, and the row keeps offering Download. A broken download is usually the network; retry after it is back.
Download failsThe log drawer names the release, the asset and the HTTP status. The usual cause is a release without this platform's server, or no network. Retry when the release carries the platform or the network is back.
Status stuck on Server starting…A cold start really can take several minutes — the executable is unpacked and virus-scanned by Windows before anything runs (the 2.7 GB CUDA one especially). Synapic waits patiently and keeps logging Still waiting for port file meanwhile; the log names the wait budget for your bundle. If it exceeds that, the log says why; see Troubleshooting: the inference server.
stale build, rebuild recommended, or Update available on a rowDeveloper checkouts only: the server executable is older than the inference source it was built from. Use Download on that row, or hand-replace the file with a fetched release; a running server is stopped and started again on the replacement.
