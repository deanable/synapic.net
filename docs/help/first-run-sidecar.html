Build the inference server

The model does not run inside Synapic. It runs in a second program, the inference server, which Synapic starts and talks to over a local port. Until one exists, the wizard is disabled on purpose.

Why there is a separate server

The model needs a Python deep-learning runtime — hundreds of megabytes of native libraries that have nothing to do with a desktop UI. Keeping them in their own process means the app starts instantly, and a crashed model cannot take your batch down with it. Synapic spawns the server, waits for it to report healthy, sends it one request per image, and shuts it down when the app closes.

You only see it in two places: the status dot in the toolbar, and the build panel below it.

Building one

  1. Look at the setup panel. Each row is a variant you can get on this machine: CPU (runs anywhere) and, on Windows, CUDA (NVIDIA GPU) (much faster on a supported card). The small grey text next to the name is the variant's runtime identifier, for example win-x64 or win-x64-cuda.
  2. Press Build sidecar on the row you want, or Download to skip the build entirely (see below).
  3. Watch the row. It shows a progress bar and the current stage, such as fetching Python, installing packages, or packaging. A first build also fetches a private copy of Python and the inference packages, which is why it is slow; a rebuild reuses what it can.
  4. When the row reads Built with a size, the server can start. Synapic starts it automatically; the status text moves to Server running (port …).

Or download it instead

If this copy of Synapic has no Python toolchain — a packaged install, for instance — press Download on the row instead of Build sidecar. It fetches the executable the latest GitHub release already published: about 216 MB for CPU, and for CUDA (NVIDIA GPU) two large parts that Synapic joins for you. The file lands where the build button would have written it, the row shows the same progress bar and stage text, and nothing on the machine needs Python, the packages, or a source checkout.

The two buttons produce the same thing: the release build is what the build button compiles, so a downloaded server behaves exactly like a built one. Download needs a network connection; building needs the repository and its toolchain, and works offline once its packages are cached.

Which variant should I build?

VariantWhen to choose it
CPUAlways a safe choice. Works on every machine, needs no GPU driver, and is what to build first. Tagging takes several seconds per image.
CUDA (NVIDIA GPU)When the machine has an NVIDIA card with a current driver. The build is larger (about 2.5 GB) and slower to produce, and it falls back to CPU if no usable GPU is present, so it is safe to install anywhere.

You can have both.

Building both is normal for a workstation: use the CUDA variant day to day and keep the CPU one as a fallback. They are independent executables and the build of one cannot break the other.

Updating or replacing the server

Press Update on the row. Synapic stops the server if it is running, replaces that variant's executable — building it from source when this copy has the Python toolchain, or fetching the newest released executable for that variant when it does not — and starts the server again on the replacement. A row whose executable is older than the inference source it was built from says so (Update available), which is the reminder that a fresh one exists.

You can also do it by hand, which is the way to pin a specific release rather than the newest one. The server is one self-contained executable: put the new file next to Synapic.exe, named synapic-inference.exe, replacing the existing one, then restart Synapic — for example switching a workstation to the CUDA build after buying a GPU.

Do not delete the server while Synapic is running.

A running batch will fail image by image. Stop the server from the toolbar first, close Synapic, then replace the file.

The model itself

Building a server does not download the model. The model arrives the first time an image is tagged, about 860 MB, and is cached per machine under %LOCALAPPDATA%\Synapic\models. Later runs, and other installs of Synapic on the same machine, reuse it.

Organisationally this matters in two cases: moving a machine to a faster variant does not re-download the model, and a machine with no internet access needs that folder seeded before it can tag anything. See Deploying to many machines.

When something looks wrong

What you seeWhat to do
Server not detected and no rows at allThere is no source checkout and the latest release has nothing for this machine's platform either. Install a release build that includes one.
Build fails part-wayThe log pane has the build's own output. A failed first build is usually the network (fetching Python or packages), and rebuilding after the network is back is the fix.
Download failsThe log pane names the release, the asset and the HTTP status. The usual cause is a release without this platform's server, or no network; Build sidecar is the way round it when this checkout has the toolchain.
Status stuck on Server starting…A cold start really can take up to two minutes. If it exceeds that, the log says why; see Troubleshooting: the inference server.
stale build, rebuild recommended, or Update available on a rowDeveloper checkouts only: the server executable is older than the inference source it was built from. Press Update on that row; a running server is stopped and started again on the new build.
