Similar images

The looser half of the catalog cleanup, and a separate operation from Deduplication: it scans a source for images that look alike rather than images that are the same, groups the candidates into a vertical list, and lets you decide which one to keep before acting on the rest. Use it when a folder or a catalog holds the same shot twice over — re-encoded, cropped, resaved or lightly edited — and you want one of each.

It has its own route and its own settings tab.

The sidebar offers Similar images directly below Deduplication, with Tagging and Upscaling further down. Its rules live on the Similar tab of the Settings view, not on the Dedup tab: widening one search never widens the other. See How a run works.

What makes two images similar

Both searches reduce an image to a 64-bit perceptual hash — a fingerprint of what the picture looks like rather than of its bytes — and compare fingerprints by how many bits differ. The two operations differ in one number: the threshold.

ThresholdOperationWhat it means
0.90 (Deduplication default)DeduplicationAt most six of the 64 bits may differ. Copies, resizes and re-encodes group; anything edited enough to change the picture does not.
0.85 (Similar images default)Similar imagesAt most ten bits may differ. Re-encodes, crops and light edits land in the same group as the original, along with more of the images you would call merely alike.

Lower the threshold further and the search gets looser still: at 0.80 or below it starts bridging quite different pictures that happen to share a composition or a palette, and the groups grow. It is a slider for how much you are willing to review, not a measure of quality.

Groups can chain.

Candidates are joined into groups transitively: if A matches B at the threshold and B matches C, all three are reported as one group even when A and C are further apart than the threshold allows. That is usually what you want for a burst of near-identical shots, and it is the reason a loose threshold can produce a big group out of images that are not all alike. Scan a small scope first if the numbers matter to you.

The algorithms

Every algorithm produces a different fingerprint of the same picture. The choice trades robustness against sensitivity.

AlgorithmGood at
PHashThe general-purpose default for both searches. Tolerates re-encoding, resizing and mild retouching, and is the least likely to confuse two unrelated photos.
DHashSmall images and subtle brightness differences; often picks up matches PHash misses in low-contrast sets.
AHashThe simplest and fastest. Adequate for exact copies and resizes, and the most sensitive to brightness changes.

The source it scans

The source is the shared one configured in Settings › Connection: the folder on disk, or the Daminion catalog scope (entire catalog, keyword search, shared collection or saved search), chosen on the processing view that runs. For a local source the scan covers .jpg, .jpeg, .png, .tif and .tiff, subfolders included. For the catalog source, items the catalog has already hashed are compared without downloading them; the rest are downloaded to a temporary file, hashed and deleted again — one at a time, so a big collection never lands on disk whole.

Running the search

  1. Set the Algorithm and the Similarity threshold on Settings › Similar. For a catalog source the Server hash rule decides how Daminion's own content hashes are compared: Exact (the default) trusts only identical values, Hamming compares them at the threshold like the algorithmic hashes.
  2. Press Search. Progress is reported as files are hashed: Hashed 240/1500… — or as items are grouped from the catalog's own hashes or downloaded for hashing.
  3. Read the summary: 1500 files scanned — 9 groups, 21 similar images, or the guidance line that says nothing matched and points at the threshold.

Reviewing the groups

Groups appear as cards in a vertical list. Each card shows how many images it holds and lists them as rows — a small preview thumbnail, name, capture date and file size — every row with its own checkbox. Previews are scaled down in memory as the list loads; nothing is saved to disk. A checked item is kept; the action applies to the unchecked ones.

Instead of ticking rows by hand, use the Keep-set rules on Settings › Similar: Oldest, Newest, Smallest and Largest. Each active switch ticks the item it names in every group; several switches tick the union of their picks. Ties go to the earlier item in the group, items with no date or size are never picked, and toggling a switch recomputes the whole selection — hand tweaks after that stick until you toggle a switch again. With no switch active, the first item of each group is kept.

Read the group list before applying anything.

Similar groups are bigger and more arguable than duplicate groups, and the default keep-set is the first file the scan found, not the best one. Work through a couple of groups by eye before you apply a bulk action, and prefer Move to folder… over a delete while you are learning what the threshold does.

ActionWhat it actually does
Delete from disk (local source)Deletes the unchecked files permanently. This is a real delete, not a move to the Recycle Bin, and there is no undo — so a confirmation prompt appears first, counting the files and saying so.
Move to folder… (local source)Moves the unchecked files into the folder you pick — a destination box appears beside the action when this is selected. Nothing is destroyed, duplicates of the same name get a numbered suffix instead of overwriting, and the destination folder is remembered for next time. It must not be inside the scanned folder.
Tag (local source)Not implemented in this version. It records the intent in the log and changes nothing.
Delete from catalog (Daminion source)Removes the unchecked items from the Daminion catalog. The original files on the server are not touched, but the catalog entries are: a confirmation prompt appears first, and after that there is no undo. The scan itself changes nothing — only Apply does.

When a search does not do what you expected

Every stage writes to logs\synapic.log beside the executable:

  • One line at the start names the source, the algorithm, the threshold, the maximum dimension and (for the catalog source) the server-hash rule.
  • One line per skipped item: an original that would not download, or a file whose hash could not be computed, is listed with the item id, the file name and the reason — items are never dropped silently.
  • One line when hashing finishes with how many items were hashed, how many were skipped, and how many groups were found.
  • One line per action: what is about to happen, then the result, then what the follow-up read confirmed.

What this tool is not

  • It does not find images by content or subject — a cat is not similar to another cat. It compares fingerprints, so two photographs of the same scene from different angles will usually stay apart.
  • It is not a replacement for Deduplication: exact copies are what that search is for, it is stricter about them, and it is the cheaper pass. Resolve the duplicates first, then use this search for what is left.
  • It does not remember a search between sessions, and it does not watch a folder. Each search is a fresh pass.
