Similar images

The looser half of the catalog cleanup, and a separate operation from Deduplication: it scans a source for images that look alike rather than images that are the same, groups the candidates into a vertical list, and lets you decide which one to keep before acting on the rest. Use it when a folder or a catalog holds the same shot twice over — re-encoded, cropped, resaved or lightly edited — and you want one of each.

It has its own route and its own settings tab.

The sidebar offers Similar images directly below Deduplication, with Tagging and Upscaling further down. Its rules live on the Similar tab of the Settings view, not on the Dedup tab: widening one search never widens the other. See How a run works.

What makes two images similar

Both searches reduce an image to a 64-bit perceptual hash — a fingerprint of what the picture looks like rather than of its bytes — and compare fingerprints by how many bits differ. The two operations differ in one number: the threshold.

ThresholdOperationWhat it means
0.90 (Deduplication, PHash)DeduplicationAt most six of the 64 bits may differ. Copies, resizes and re-encodes group; anything edited enough to change the picture does not.
0.85 (Similar images, PHash)Similar imagesAt most ten bits may differ. Re-encodes, crops and light edits land in the same group as the original, along with more of the images you would call merely alike.

Those two numbers assume PHash, the default fingerprint. DHash and AHash are coarser — they place two different pictures much closer together — so each carries a tighter starting threshold of its own: DHash 0.97 for duplicates and 0.91 for similar images, AHash 0.99 and 0.94. Changing the algorithm moves a threshold you have not touched to that algorithm's default.

Lower the threshold further and the search gets looser still: below about 0.85 it starts bridging quite different pictures that happen to share a composition or a palette, and the groups grow. It is a slider for how much you are willing to review, not a measure of quality.

Groups can chain.

Candidates are joined into groups transitively: if A matches B at the threshold and B matches C, all three are reported as one group even when A and C are further apart than the threshold allows. That is usually what you want for a burst of near-identical shots, and it is the reason a loose threshold can produce a big group out of images that are not all alike. Scan a small scope first if the numbers matter to you.

The algorithms

Every algorithm produces a different fingerprint of the same picture. The choice trades robustness against sensitivity.

AlgorithmGood at
PHashThe general-purpose default for both searches. Tolerates re-encoding, resizing and mild retouching, and is the least likely to confuse two unrelated photos.
DHashSmall images and subtle brightness differences; often picks up matches PHash misses in low-contrast sets.
AHashThe simplest and fastest. Adequate for exact copies and resizes, and the most sensitive to brightness changes.

The source it scans

The source is the shared one configured in Settings › Connection: the folder on disk, or the Daminion catalog scope (entire catalog, keyword search, shared collection or saved search), chosen on the processing view that runs. For a local source the scan covers .jpg, .jpeg, .png, .tif and .tiff, subfolders included. The catalog source is downloaded and fingerprinted the same way, one item at a time and deleted again as soon as it is hashed, so a big collection never lands on disk whole. It does not reuse Daminion's own server hash: that is a content hash, which can say two items are the same file but nothing about whether two images look alike. The Deduplication operation is the one that uses it, and the similarity search hashes pixels so the algorithm and threshold apply to every item.

Running the search

  1. Set the Algorithm and the Similarity threshold on Settings › Similar. Those two rules apply to every item in the scope, local or catalog.
  2. Press Search. On a catalog source the search first gathers every item in the scope, 500 records per request, showing Fetching items from Daminion: 1,500 of 47,851… on a large catalog — the Max items ceiling does not apply here, because a similar image outside the fetched prefix would be reported as unique. The walk keeps going until the search's own record count is in hand: if the catalog stops answering at a later page position, it carries on using the page number instead of the offset, so a scope larger than one page is still gathered whole. The shared Run bar tracks that walk as well: records fetched of the scope total, the page it is on, and an estimate of the time left, then it switches to hashing progress. Progress is reported as files are hashed: Hashed 240/1500… — or, on a catalog source, as each item is downloaded for hashing.
  3. Read the summary: 1500 files scanned — 9 groups, 21 similar images, or the guidance line that says nothing matched and points at the threshold.
  4. On a catalog source the scan card also shows the walk's read-only retrieval numbers under the summary: Counted (the scope count), Page total (what the pages themselves said), Pages, Raw scanned and Kept. A count that disagrees with what was kept is called out there, so a short read is visible without opening the log; the page-level detail stays in logs\synapic.log. On such a disagreement Re-walk using page totals runs the walk again with each page's own total steering the bar instead of the scope count — a second pass can clear a transient short read — and Export report writes these numbers and the comparison to a text file in Documents. Neither changes the catalog.

Reviewing the groups

Groups appear as cards in a vertical list. Each card shows how many images it holds and lists them as rows — a small preview thumbnail, name, capture date and file size — every row with its own checkbox. Previews are scaled down in memory as the list loads; the preview itself is never written to disk (the search's fingerprints and row details are — see Coming back to a search below). A checked item is kept; the action applies to the unchecked ones.

Adjusting the sensitivity after a search

The Threshold slider on the search card re-filters the results already on screen. It appears once a search has produced fingerprints; moving it re-groups those fingerprints without hashing or re-reading an original, so an ordinary library updates almost instantly. (A preview is fetched only for an item that newly enters a group.) The value settles about a third of a second after you stop moving, which is what keeps one drag from starting dozens of recalculations; a very large catalog (tens of thousands of images) can take up to a second, and the card shows a progress line while it does.

The keep checkboxes you set survive a re-filter: an item you unchecked stays unchecked while it is still in a group, and an item that only appears at the new threshold starts out kept, as it would after a search. The slider writes the same setting as Settings › Similar, so the value you settle on is the one the next search starts with. Changing the Algorithm needs a fresh search — the stored fingerprints belong to the algorithm that produced them. After Apply the slider steps aside too, because the files it would re-group have changed.

Coming back to a search

The last search of a source is remembered when you close the app. Its fingerprints and the row details (name, date, size) are stored under %LOCALAPPDATA%\Synapic\fingerprints — one file per operation and source, the newest eight per operation kept, no image copies — so reopening the app with the same folder or catalog scope shows the same results, and the Threshold slider is live at once: no hashing and no catalog walk. Nothing is restored under a different algorithm, and pointing the source somewhere else shows nothing until that source is searched. A saved result that holds only the catalog's content hashes — what an older build stored for this operation — is not restored: the search hashes pixels, so that result is rescanned rather than shown. Scan still re-reads the source and replaces the saved copy, and Apply discards it, because the files it described have changed. Deleting the fingerprints folder is safe: the next search simply rebuilds it.

Instead of ticking rows by hand, use the Keep-set rules on Settings › Similar: Oldest, Newest, Smallest and Largest. Each active switch ticks the item it names in every group; several switches tick the union of their picks. Ties go to the earlier item in the group, items with no date or size are never picked, and toggling a switch recomputes the whole selection — hand tweaks after that stick until you toggle a switch again. With no switch active, the first item of each group is kept.

Read the group list before applying anything.

Similar groups are bigger and more arguable than duplicate groups, and the default keep-set is the first file the scan found, not the best one. Work through a couple of groups by eye before you apply a bulk action, and prefer Move to folder… over a delete while you are learning what the threshold does.

ActionWhat it actually does
Delete from disk (local source)Deletes the unchecked files permanently. This is a real delete, not a move to the Recycle Bin, and there is no undo — so a confirmation prompt appears first, counting the files and saying so.
Move to folder… (local source)Moves the unchecked files into the folder you pick — a destination box appears beside the action when this is selected. Nothing is destroyed, duplicates of the same name get a numbered suffix instead of overwriting, and the destination folder is remembered for next time. It must not be inside the scanned folder.
Tag (local source)Not implemented in this version. It records the intent in the log and changes nothing.
Delete from catalog (Daminion source)Removes the unchecked items from the Daminion catalog. The original files on the server are not touched, but the catalog entries are: a confirmation prompt appears first, and after that there is no undo. The scan itself changes nothing — only Apply does.
Reject in catalog (Daminion source)Marks the unchecked items Rejected in the Daminion catalog (the red reject flag) instead of deleting them — the layer for going through the identified images by hand in Daminion first and deciding there. Nothing is deleted and no prompt appears: rejecting is reversible. The write is read straight back, so the summary only reports success when the server really applied the flag; acted-on rows leave the review list and the group list keeps what is left. The scan itself changes nothing — only Apply does.

When a search does not do what you expected

Every stage writes to logs\synapic.log beside the executable:

  • One line at the start names the source, the algorithm, the threshold, the maximum dimension and (for the catalog source) the server-hash rule.
  • One line per skipped item: an original that would not download, or a file whose hash could not be computed, is listed with the item id, the file name and the reason — items are never dropped silently.
  • One line when hashing finishes with how many items were hashed, how many were skipped, and how many groups were found.
  • One line per action: what is about to happen, then the result, then what the follow-up read confirmed.

What this tool is not

  • It does not find images by content or subject — a cat is not similar to another cat. It compares fingerprints, so two photographs of the same scene from different angles will usually stay apart.
  • It is not a replacement for Deduplication: exact copies are what that search is for, it is stricter about them, and it is the cheaper pass. Resolve the duplicates first, then use this search for what is left.
  • It does not remember a search between sessions, and it does not watch a folder. Each search is a fresh pass.
