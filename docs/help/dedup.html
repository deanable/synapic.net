Deduplication

A separate operation, not part of tagging: it scans a source for images that look the same, groups the candidates into a vertical list, and lets you decide which copies to keep before acting on the rest. The source is either a local folder or the Daminion catalog — the same choice the data source makes for tagging.

It has its own route.

The sidebar offers Deduplication beside Tagging and Upscaling, with Similar images — the looser search for visually alike pictures, documented in Similar images — directly below it. Each is a view of its own rather than a step in a shared chain, and the source it runs over — the same one tagging uses — is configured in the Settings view. See How a run works.

The source it scans

  1. Deduplication reads the shared source, so there is no second source to choose. The catalog side reuses the scope chosen on the processing view that runs — for tagging that is the Tagging view (entire catalog, keyword search, shared collection or saved search). The summary is shown above the scan button.
  2. For a local source, the folder is the one set in Settings › Connection. Subfolders are included automatically, and the scan covers .jpg, .jpeg, .png, .tif and .tiff. For the catalog source, items the catalog has already hashed are compared without downloading them; the rest are downloaded to a temporary file, hashed and deleted again — one at a time, so a big collection never lands on disk whole.

Nothing is cached — and the temporary folder is swept.

Synapic keeps no downloaded image between scans: previews are rendered in memory, and the originals it pulls sit in %TEMP%\synapic_daminion only for the moment it takes to hash them. A download that dies half-way is deleted on the spot, and files a crash or a power cut left behind are swept at every launch and again before each scan (anything younger than an hour is kept, so a download that is still running is never touched). The log names the folder and, after every scan, reports what it still holds — which should read zero files.

Scanning

  1. The algorithm and the Threshold come from Settings › Dedup; the defaults are a good starting point. For the catalog source the Server hash rule decides how the catalog's own content hashes are compared: Exact (the default) trusts only identical values, Hamming compares them by similarity at the threshold. (Only this operation can use the server hash — Similar images always hashes pixels, because a content hash says nothing about whether two images look alike.)
  2. Press Scan. On a catalog source the scan first gathers every item in the scope, 500 records per request, showing Fetching items from Daminion: 1,500 of 47,851… on a large catalog — the Max items ceiling does not apply here, because a duplicate outside the fetched prefix would be reported as unique. The walk keeps paging until the search's own record count is in hand, using the page number rather than the offset if the catalog stops answering at a later position, so the whole scope is gathered. The shared Run bar tracks that walk as well: records fetched of the scope total, the page it is on, and an estimate of the time left, then it switches to hashing progress. Progress is reported as files are hashed: Hashed 240/1500… — or as items are grouped from the catalog's own hashes or downloaded for hashing.
  3. Read the summary: 1500 files scanned — 12 groups, 18 duplicates.
  4. On a catalog source the scan card also shows the walk's read-only retrieval numbers under the summary: Counted (the scope count), Page total (what the pages themselves said), Pages, Raw scanned and Kept. A count that disagrees with what was kept is called out there, so a short read is visible without opening the log; the page-level detail stays in logs\synapic.log. On such a disagreement Re-walk using page totals runs the walk again with each page's own total steering the bar instead of the scope count — a second pass can clear a transient short read — and Export report writes these numbers and the comparison to a text file in Documents. Neither changes the catalog.

Algorithms and the threshold

Every algorithm reduces an image to a 64-bit perceptual fingerprint. Two images are "the same" when their fingerprints differ by no more than the threshold allows. Each fingerprint has its own starting threshold, because they are not on one scale: PHash starts at 0.90, DHash at 0.97 and AHash at 0.99. DHash and AHash put two different pictures far closer together, so they need the tighter budget — and because they do, changing the algorithm moves a threshold you have not touched to that algorithm's own default.

PHashThe general-purpose default. Tolerates re-encoding, resizing and mild retouching, and is the least likely to confuse two unrelated photos.
DHashSmall images and subtle brightness differences; often picks up duplicates PHash misses in low-contrast sets.
AHashThe simplest and fastest. Adequate for exact copies and resizes, and the most sensitive to brightness changes.

0.90 (PHash default)Close matches only. Start here: it finds copies and re-encodes with few false groups.

Scan a copy first if the stakes are high.

Scan the folder, look at the groups, and only then decide on an action. The scan itself changes nothing: it reads files and hashes them.

Reviewing the groups

Groups appear as cards in a vertical list. Each card shows how many images it holds and lists them as rows — a small preview thumbnail, name, capture date and file size — every row with its own checkbox. Previews are scaled down in memory as the list loads (for the catalog source they come straight from the server's thumbnail endpoint); the preview itself is never written to disk (the scan's fingerprints and row details are — see Coming back to a scan below). A row whose image cannot be decoded simply shows no thumbnail. A checked item is kept; the action applies to the unchecked ones.

Adjusting the sensitivity after a scan

The Threshold slider on the scan card re-filters the duplicates already on screen. It appears once a scan has produced fingerprints; moving it re-groups those fingerprints without hashing or re-reading an original, so an ordinary library updates almost instantly. (A preview is fetched only for an item that newly enters a group.) The value settles about a third of a second after you stop moving, which keeps one drag from starting dozens of recalculations; a very large catalog can take up to a second, and the card shows a progress line while it does.

The keep checkboxes you set survive a re-filter: an item you unchecked stays unchecked while it is still in a group, and an item that only appears at the new threshold starts out kept. The slider writes the same setting as Settings › Dedup, so the value you settle on is the one the next scan starts with. Changing the Algorithm needs a fresh scan — the stored fingerprints belong to the algorithm that produced them. After Apply the slider steps aside too, because the files it would re-group have changed.

Coming back to a scan

The last scan of a source is remembered when you close the app. Its fingerprints and the row details (name, date, size) are stored under %LOCALAPPDATA%\Synapic\fingerprints — one file per operation and source, the newest eight per operation kept, no image copies — so reopening the app with the same folder or catalog scope shows the same review list, and its Threshold slider works at once: no hashing, no catalog walk, no download. Nothing is restored under a different algorithm, and pointing the source somewhere else shows nothing until that source is scanned. Scan still re-reads the source and replaces the saved copy, and Apply discards it, because the files it described have changed. Deleting the fingerprints folder is safe: the next scan simply rebuilds it.

Instead of ticking rows by hand, use the Keep-set rules in Settings › Dedup: Oldest, Newest, Smallest and Largest. Each active switch ticks the item it names in every group; several switches tick the union of their picks. Ties go to the earlier item in the group, items with no date or size are never picked, and toggling a switch recomputes the whole selection — hand tweaks after that stick until you toggle a switch again. With no switch active, the first item of each group is kept.

Read the group list before applying anything.

The default keep-set is the first file the scan found, not the best one — use the auto-select switches or tick rows yourself when the order is wrong. A group of two is easy to read; a group of nine is worth opening a couple of.

Delete from catalog (Daminion source)Removes the unchecked items from the Daminion catalog. The original files on the server are not touched, but the catalog entries are: a confirmation prompt appears first, and after that there is no undo. The scan itself changes nothing — only Apply does.

After an action the groups it touched are removed from the list and the summary reports the result, for example Moved 4 duplicate(s) to …. Anything that failed is in the log.

When a scan does not do what you expected

Every stage of a scan writes to logs\synapic.log beside the executable, so a scan that hashes fewer files than the scope holds, or an action that does not stick, can be read rather than guessed at:

  • One line at the start names the source (folder, or scope and id), the algorithm, the threshold, the maximum dimension and (for the catalog source) the server-hash rule.
  • One line per skipped item: an original that would not download, or a file whose hash could not be computed, is listed with the item id, the file name and the reason — items are never dropped silently.
  • One line when hashing finishes with how many items were hashed and how many were skipped, then one with the number of groups found.
  • One line per action: what is about to happen (the ids for a catalog delete), then the server's own answer, then whether the follow-up read confirms it.

What this tool is not

  • It does not find similar images by content or subject. This search looks for perceptually equal copies; if you want the visibly alike ones — re-encoded, cropped or lightly edited versions — that is the Similar images operation, at a looser threshold.
  • It does not remember a scan between sessions, and it does not watch a folder. Each scan is a fresh pass.
