Step 4 — Results

One row per image, with what the model produced and what happened to it. This is where you confirm a run did what you meant, before you widen it to the rest of the library.

The summary line

40 succeeded (0 verified), 2 failed, 42 total

The verified count only moves when you ask Synapic to re-read a Daminion catalog. On a folder run it stays at zero, and that is not a problem — the file was written, and there is nothing to re-read.

The grid

ColumnWhat it shows
FileThe image's file name.
StatusThe outcome for that image (see below).
CategoryThe category the model produced.
KeywordsThe keyword list, joined for readability.
DescriptionThe one-line description.

Columns are sortable, which is the quickest way to see the trouble: sort by Status to put every failure together, or by Description to spot the vague ones.

What the statuses mean

StatusMeaning
SuccessThe image was tagged and the result was written.
Write FailedThe image was tagged, but writing the result failed — a permissions problem on a folder, or a metadata update Daminion refused. The model's output is still in the row, so nothing was wasted.
VerifiedA Daminion item whose stored metadata was re-read and matched what Synapic wrote.

"Success" means written, not "the model was right".

Rows record what happened, not whether the tags are good. A run that writes twenty wrong keywords still reports twenty successes. The only honest check of quality is looking at the images — and at a few items in Daminion.

The buttons

ButtonWhat it does
Export CSVWrites the whole result set to Documents\synapic_results_<timestamp>.csv, with columns for file name, status, tags, category, keywords, description, probabilities and scoring tier. Useful when a curator wants to review the run away from Synapic.
Retry FailedRe-does only the rows whose status is not a success. Synapic re-fetches those items from the source, drops the old failed entries, and runs them again with the current settings. Fix the cause first — a missing file will fail the same way twice.
Verify Daminion WritesAvailable when Step 1 has a live Daminion connection. Re-reads the metadata of each successful Daminion item and compares it with what was supposed to be written: matching items become Verified, mismatches are listed in the summary and the log.
RefreshReloads the grid from the run's results. Use it after a retry or a verification.

Verification is the answer to "did it actually stick?"

After a large Daminion run, press Verify Daminion Writes and read the summary. If it reports mismatches, the write path is the problem — permissions, a locked item, or a field Daminion would not accept — and you have found that out before announcing the run as finished.

A sane routine after a run

  1. Read the summary line: any failures at all?
  2. Sort by Status to see them, and check the log for the reasons.
  3. On a Daminion run, verify the writes.
  4. Open two or three of the images in Daminion and look at what landed. This is the only step that catches a run that was technically perfect and creatively wrong.
  5. Export the CSV if someone else needs to review it.

Related topics

The results grid is a report, not a control panel: there is no way to edit a tag here and push it back. To change an outcome, adjust Step 2 and run the affected items again — a re-run replaces the fields Synapic manages, so it is safe to repeat.
