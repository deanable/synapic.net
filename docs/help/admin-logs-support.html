Logs, crashes and support

Every run leaves an honest record. Knowing where it is turns most support conversations into a single attachment.

Where the logs are

FileContents
logs\synapic.logThe current run, written as it happens. It starts empty on each app start.
logs\archives\synapic-<date>-<time>.logPrevious runs. Each start moves the old log here and keeps the ten most recent, so a week of work is usually still on disk.
logs\crashes\crash-<stamp>-<source>.txtOne file per crash, holding the exception and a snapshot of the log at that moment. The most recent reports are kept.
logs\synapic-usage.jsonOpt-in local counters: batches run, items processed, duplicates found. No service is contacted, ever.

The folder is next to the executable — C:\Program Files\Synapic\logs on a default install. If that folder is not writable, Synapic falls back to %LOCALAPPDATA%\Synapic\logs, and says so in the UI log when it starts. Check there first if the expected folder is empty.

The log's level is a config setting.

ui.logLevel in config.json defaults to info. Internal debugging detail (including per-field model output) is logged at a level you will not see in the file; the UI log pane and the batch's own lines are what to read instead. See Files, folders and registry keys.

What a log tells you

  • What settings a run used. The batch's first line names the tag fields being written, which settles a whole class of "fields are missing" reports without any guesswork. See Tag fields.
  • What each image produced. A result line per image with the category, the keyword count and the start of the description.
  • Why an image failed. A failure line with the reason, matched to the row in Step 4.
  • What the inference server said. Its error stream is passed through verbatim, prefixed [sidecar:err], which is where model-loading and packaging problems surface.

Reading the log explains the individual lines.

What to send with a support request

  1. logs\synapic.log for the session in question.
  2. If the problem started earlier, the matching file from logs\archives\ — the file names carry the run's start time.
  3. Anything in logs\crashes\, especially if the app closed unexpectedly.
  4. Which version and which inference server variant: read them from the status area and the setup panel — for example Server running (port 51234) plus a server row reading Built with its variant and size.
  5. One sentence on the expectation: what you asked for and what happened instead. The log records the settings, not your intent.

Reproduce it small.

Most problems worth reporting can be shown with a single folder of five images, or one Daminion item. A small reproduction makes the log a few dozen lines instead of fifty thousand, and the answer usually arrives faster.

Privacy in the logs

AppearsDoes not appear
File names and folder pathsImage contents, which never leave the machine
The Daminion server URL and usernameThe Daminion password, which is stored separately and encrypted
Model ids, device, settings and error messagesAnything about other applications on the machine

Logs are text files in the install folder, so normal file-retention rules apply: delete or archive them as your policy requires. Nothing is transmitted anywhere by the app itself.

Two practical gotchas

  • An empty-looking help file. If Synapic.chm opens with blank pages or a missing Contents pane, Windows has blocked it as an attachment. Right-click the file, choose Properties, tick Unblock, and reopen. Copies distributed over a network share hit this too.
  • A log folder that is empty after a crash. The app could not write to the install folder. Look in %LOCALAPPDATA%\Synapic\logs; a crash before logging initialised is the one case where there is genuinely nothing to read.
